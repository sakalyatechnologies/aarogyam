# v10 T4: wait timer and collect race rules (handoff)

Branch `v10-t4`. Files: `desk/WaitTimerHolder.kt`, `desk/DeskPayment.kt`, `desk/DeskPaymentDelivery.kt`, tests `WaitTimerHolderTest`, `DeskCollectRaceTest`. No seam edits needed.

## Public API for iOS (T7)

`graph.waitTimer(clinic:scope:)` returns `WaitTimerHolder`:
- `state: StateFlow<WaitTimerState>`: `Loading`, `Failed(error)`, `Ready(entries)`.
- `WaitEntry`: `tokenId`, `tokenNumber`, `doctor` (nullable), `elapsedSeconds`, `state` (`WaitState.Fresh` under 60 s, `NoReply` from 60 s), `clock` ("0:42"), `checkWithKey` (`CHECK_WITH_DOCTOR_KEY` = "wait.check_with_doctor" when NoReply, else null). The screen formats "Check with Dr X" itself from `doctor`.
- Only waiting tokens with no `called_at` appear; a called token drops out on the next `refresh()`.
- `refresh()` reloads `/queue` (call on live update or poll), `tick()` recomputes from the clock (the holder also ticks itself every 1 s), `canRemind` is false (follows `ServerCaps.queueRemind`, no detector yet), `remind(tokenId)` does nothing (G1 not shipped).

`DeskPaymentStateHolder` (built by the existing `graph.deskPayment`) now adds:
- `DeskPayOutcome.AlreadyPaid`: balance was 0 on the re-GET (or after a 409); nothing was sent. Swift `switch` on the outcome needs a case.
- `cardOpen: StateFlow<Boolean>`: false when the notification is handled or the bill list has no balance.
- `checkHandled(notificationId)`: reads `/notifications` by hand; closes the card when that `collect_payment` row has a non-null `handled`. Call it on the live update / bell refresh for the To-pay card's notification id.
- `doctorMayBeCollecting(tokenStatus, visitEndedAt)`: `ready_to_bill` and the visit's `ended_at` (ISO string) under 2 minutes ago, on the holder's injected clock (constructor param `clock`, defaulted).

## Race rules (in `record`)
1. Online: `recheck` re-GETs `/invoices/{id}` first. Issued with balance 0 gives AlreadyPaid. Issued with a balance allocates `min(amount, balance)`. Draft sets issue-first (issue, then pay). Void is refused. A retryable re-GET failure saves the payment ("Saved, will send"); other failures show Failed.
2. A 409 from `POST /payments` (`Delivery.Rejected.conflict`) re-GETs the bill, reloads the list, and shows AlreadyPaid if the balance is 0, else Failed.
3. The idempotency key is unchanged: one client id per attempt.
4. The re-GET runs only on the online path. The outbox sender (`deliver`) is unchanged and still issues-first and allocates from the queued job.

## Tests (commonTest, fake API, injected clock)
59 s Fresh and 60 s NoReply; called token leaves; Remind off and sends nothing; re-GET before payment (balance sets allocation); zero balance sends nothing; draft issued first; 409 refetch (paid and not paid); handled closes the card; unhandled or no `handled` field keeps it open; zero balance closes the card; doctorMayBeCollecting at 0/119 s true, 120/600 s false, not ready_to_bill false, plus the holder's clock. `until {}` helper waits in real time because the mock engine answers on other threads.

## Gaps
- `ServerCaps.notificationAudience` is marked by `collectNotices()` when any notification row has `handled` or `audience`; before the first read the flag is off and `checkHandled` closes nothing.
- No push or SSE hook: the screen must call `checkHandled` itself.
- The offline-sent payment does not re-GET (server 409 then lands as a rejected outbox entry).
- `doctorMayBeCollecting` needs the visit's `ended_at`; T7 must pass it (visit list needs `clinical.read`).
