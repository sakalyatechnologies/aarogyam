# Mobile architecture

Status: decided 5 Oct 2026. Scope: the Aarogyam staff app (doctors, front desk, owners) on Android and iOS. The patient app follows the same architecture once the patient-accounts API (P2 in `patient-access.md`) exists.

## Goals

1. One place for logic: everything that isn't drawing pixels lives in Kotlin Multiplatform and is tested once.
2. Native feel: Jetpack Compose on Android, SwiftUI on iOS, platform navigation, platform pickers, platform speech.
3. The API contract is generated, never copied by hand (MyDwarpal drifted: hand-copied enums, three login response shapes).
4. Safe by default: tokens in Keychain/Keystore, no patient data in logs, screenshots blocked on clinical screens, app lock.
5. Online-first with a durable draft queue (decision 2026-10-02): a read cache and an outbox, no sync engine in 1A.

## Repositories and modules

                           Android Keystore AES-GCM + DataStore
  outbox/                  durable queue on SQLDelight: submissions with idempotency keys, exponential backoff,

  design/                  theme from a brand colour and mode, ported from sakalya-web's tokens package and
                           checked against the same test vectors; spacing, radii, type scale
  design-compose/          Compose components on top of design/ (buttons, fields, cards, chips, list rows)
  ios/SakalyaUI/           Swift package: SwiftUI components on top of design/ (same set)

  shared/                  KMP: generated API client (from docs/api/openapi.json), repositories per feature,

`sakalya-mobile` is consumed as a Gradle composite build of a pinned tag: `scripts/mobile-deps.sh` checks out the tag named in `mobile/sakalya-mobile.version` into `mobile/.deps/` (git-ignored). Publishing to a private Maven repository replaces this when CI arrives. Generic code found in `aarogyam/mobile` moves to `sakalya-mobile` under AGENTS.md rule 13.

The earlier plan named `sakalya-android` and `sakalya-ios`; with Kotlin Multiplatform one repository holds both, plus one Swift package for SwiftUI components.

## Talking to the API

- **Tenancy stays host-based (product rule 1).** The app signs in, calls `GET /api/v1/me` on the app host, lists the person's clinics with their hosts, and talks to `https://<clinic host>/api/v1/...` for clinic work. The clinic is never sent in a header or body.
- **Environments:** `local` uses `http://<slug>.localtest.me:5173` (the Vite dev server proxies `/api` with the right host; Android needs `adb reverse tcp:5173 tcp:5173`; cleartext only in debug builds); `demo` uses the workers.dev hosts; `prod` the product domain.
- **Generated client:** OpenAPI Generator, `kotlin` generator with the `multiplatform` library (Ktor + kotlinx.serialization), output under `shared/build/generated`. A test fails when `docs/api/openapi.json` changed but the client wasn't regenerated.
- **Every request carries:** `x-request-id` (UUID v7), `x-client: aarogyam-staff/<version>`, `x-device-id` (random, stored securely), platform and OS version (header-safe). Mutations carry `Idempotency-Key`, one per submission, rotated only after success.
- **Errors:** one `ApiError(code, message, status, requestId)`; screens map codes to copy; messages never include patient data.

## Sign-in and session

- The app calls Supabase Auth directly (email code; the API only verifies tokens). Sign-ups stay off; invitations create accounts.
- Tokens live only in secure storage. Refresh is single-flight: the first 401 refreshes, others wait, each request retries once.
- **Only a rejected refresh signs the person out.** Network errors, 429 and 5xx keep the session (MyDwarpal logged people out on a network blip at cold start).
- Sign-out: unregister push (later), revoke the session on the API, clear secure storage and the cache.
- App lock: biometric or device passcode after 5 minutes in the background, and on cold start when a session exists.

## Screens and state

- Each screen has a state holder in `shared` exposing `StateFlow<UiState>` and functions for intents. UI code only renders and forwards events. Business rules are tested in `commonTest`.
- iOS consumes Kotlin through SKIE (flows as `AsyncSequence`, sealed classes as Swift enums, suspend functions as `async`).
- Budget: a screen file stays under about 300 lines; anything larger is split.
- Navigation is native per platform (Compose Navigation, `NavigationStack`).

## Offline (1A)

- **Read cache:** today's schedule, the queue and recently opened patients, in SQLDelight, shown immediately and refreshed from the API.
- **Outbox:** note drafts, vitals, voice recordings and queue actions go through the outbox with their idempotency keys and retry until delivered or expired (48 h), with a visible "waiting to send" state.
- **Conflicts:** the server is the authority. Signed clinical records are never merged; a collision becomes a separate note marked `conflict` (decision 2026-10-02).
- Device storage relies on Android file-based encryption and iOS Data Protection (`completeUntilFirstUserAuthentication`), plus the app lock. The cache holds only what the staff member could see on the web.

## Security and privacy

- `FLAG_SECURE` on clinical screens on Android; iOS hides content in the app switcher and blurs on screen capture.
- The logger redacts by default: IDs only, no names, phone numbers, notes or URLs with tokens. Release builds drop debug logs.
- No certificate pinning (Cloudflare rotates certificates); TLS with platform trust. Play Integrity and App Attest come with public launch.
- Uploads (voice notes, photos, X-rays) go through the attachments API; files are never stored in the database.

## Voice notes

Recording with `MediaRecorder` / `AVAudioRecorder`; live dictation with Android `SpeechRecognizer` and iOS `SFSpeechRecognizer` (en-IN, hi-IN, mr-IN; on-device where available). The recording uploads through the outbox, linked to the note.

## Quality gates

- `commonTest` with Ktor `MockEngine` for every library and state holder; run on JVM and the iOS simulator.
- Android: unit tests, Compose UI tests for key screens, Android Lint with warnings as errors, ktlint.
- iOS: XCTest for the Swift layer, SwiftLint.
- The pre-commit hook runs the mobile gate when `mobile/` or `sakalya-mobile` changes: `./gradlew check` and an iOS simulator build.
- End to end: Maestro flows (sign-in, Today, book, visit and note, offline and backgrounding), as MyDwarpal does, with a test sign-in path that doesn't hit email throttles.

## Release (later)

Fastlane lanes per platform: `beta` (Play internal testing, TestFlight), `production` (Play draft, App Store stopping before review), screenshots and metadata, preflight checks that fail on missing signing config. Versions from git tags. Crash reporting with user context added only when wired to call sites (MyDwarpal built analytics that were never called).

## Build order

1. `sakalya-mobile`: core, http, auth, secure-storage, outbox, design with tests; tag v0.1.0.
2. `aarogyam/mobile`: generated client, AppGraph, sign-in, clinic picker and Today end to end on both platforms (the reference screens).
3. Feature screens, delegated by pattern: patients and Patient 360, calendar and booking, queue, visit (notes, vitals, voice, dental chart summary), prescriptions (Quick Rx, issue), billing (bills, record payment).
