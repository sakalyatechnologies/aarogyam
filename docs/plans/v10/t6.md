# T6: My tasks holder and notification kinds

Kotlin only. Branch `v10-t6`. Files: `tasks/MyTasksHolder.kt`, `tasks/TaskCalls.kt`, `notifications/NotificationKinds.kt`, four task models added to `apiModels` (`MyTasks`, `TaskOccurrence`, `CompleteBody`, `UsageBody`; `Badges` was already there).

## Public API (for iOS T10 and T7)

`graph.myTasks(clinic, scope): MyTasksHolder`
- `state: StateFlow<MyTasksState>`: `loading`, `notAllowed` (role lacks `tasks.use`, nothing requested), `rows`, `openCount`, `doneCount`, `loadError` (only while nothing has loaded; a later failed refresh keeps the rows).
- `rows: List<TaskRow>`: open tasks only, overdue first, then by `due_at`. `TaskRow { id, title, action (None | RecordUsage | ConfirmPhotos; unknown acts like None), dueAt (RFC 3339, format in the clinic zone), overdue, patientsWithoutPhotos: Int?, pending, error: ScreenError? }`.
- `celebrate: SharedFlow<Unit>`: one event per task this holder finished successfully (not replayed). Collect it on the screen for confetti.
- `proofSupported: Boolean`: always false (G4). No upload exists.
- `refresh()`, `observe(live)`: like the other holders. The holder refreshes once when created.
- `complete(id, note: String?, usage: List<UsageLine>?)`: `UsageLine(itemId, quantity: Long)`. Note is trimmed, cut at 300 characters and dropped when blank. For `record_usage` pass the lines, or an empty list for "nothing used"; pass null for other tasks. The row shows `pending = true`, is removed only after the server says yes, then `celebrate` fires and the list refreshes. On failure the row stays with `error` set (`ScreenError`); calling `complete` again reuses the same `client_id`. A 409 also refreshes the list. Double taps while pending are ignored.
- `openCount` is `/me/badges.tasks_open` (counts open tasks of every day); it falls back to the number of rows when the badge call fails (that endpoint needs `chat.use`, which a role may lack).

`notifications/NotificationKinds.kt`
- `NotificationKinds.of(kind: String?): NotificationKindInfo { kind, category, icon, titleKey, known }`. Never throws, never null. Unknown or empty kinds give `category = Generic`, icon `msg`, title key `v10.notif.generic`, `known = false`.
- `NotificationCategory`: Queue, Task, TimeOff, Stock, Booking, Lab, Payment, Recall, Generic.
- Title keys: queue kinds keep the existing `d9.alert.*` keys (table DeskV9); booking kinds keep `t7.notif.requested|confirmed|cancelled` (table TodayV7); the rest are new `v10.notif.*` keys (`task_due`, `task_reminder`, `task_escalated`, `time_off_requested`, `time_off_decided`, `stock_alert`, `arrival`, `lab_overdue`, `payment_due`, `recall_due`, `generic`) that iOS must add to a table with `en`, `hi`, `mr`. Task and stock rows carry their own name (`NotificationKinds.carriesOwnTitle`): show `title` or `item_name` as the detail.
- Icons used: clock, bell, check, alert, calendar, box, msg. iOS maps these names to SF Symbols. `alert` and `box` are new names; `DeskAlert.icon` in `DeskV9Logic.swift` still has its own copy and should switch to this mapping.
- `NotificationEntry` (hand-written, all fields defaulted): `id, kind, createdAt, read, href, title, dueAt, itemName, daysCover, handled: HandledStamp?`; `isHandled` (false when `handled` is absent or null), `isUnread` (`!read && !isHandled`), `info`.
- `List<NotificationEntry>.dedupeById()` keeps the first of each id; `mergeNotifications(shown, fresh)` puts new ids first and replaces shown rows with the fresh copy, each id once (for the banner fed by poll plus live stream).
- `ClinicApi.notificationEntries(unreadOnly, limit, before)`: `GET /notifications` decoded into `NotificationEntries`. It does not call `ServerCaps.markNotificationAudience()`; the caller may when `handled` shows up.

- The title strings for the new keys do not exist in any iOS catalog yet.
- Push for these kinds is not wired (in-app only), as the handoff says.
- `AppGraph.myTasks` is unchanged and returns the interface; no seam edit is needed.
